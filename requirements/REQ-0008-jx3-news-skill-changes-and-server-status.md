# REQ-0008：剑网 3 公告、技改与开服状态

## 基本信息

- 状态：待验收
- 创建日期：2026-07-30
- 最后更新：2026-07-30
- 负责人：待定

## 背景

当前宠物快捷面板只提供宠物互动、窗口置顶和设置入口，用户无法快速查看《剑网 3》的近期官方公告、武学调整公告和服务器开服状态。

西山居 `xoyo.com` 体系内已经提供公告页面和游戏所需的服务器列表数据。JX3API 的公开接口说明也表明，它的技改与服务器状态能力分别通过筛选西山居公告、解析西山居服务器列表实现。本项目希望参考其成熟的产品行为，但直接获取并处理西山居公开页面或其页面使用的数据，不把 JX3API 作为生产依赖。

这些数据可能来自官网网页使用的内部接口，而不是西山居承诺长期兼容的正式开放 API。因此必须通过独立数据适配器、缓存、限频、错误降级和可替换实现控制变更风险。

## 目标

- 用户可以分别查看“公告”和“技改”列表。
- “公告”展示符合范围的官方公告，可以包含技改公告；“技改”只展示识别为武学调整的公告。
- 用户可以单独查询指定服务器当前处于开服、关服还是未知状态。
- 用户可以选择服务器开启监听；程序检测到服务器由关服变为开服时主动报告。
- 所有原始业务数据直接来自西山居官方域名，不要求用户配置 JX3API Token。
- 网络或官网结构异常时提供明确反馈，并尽量保留最近一次成功数据。

## 产品结构

- 在现有宠物快捷面板首页新增三个独立入口：
  - 公告；
  - 技改；
  - 开服状态。
- 点击任一入口后，在同一个快捷面板内进入该功能对应的二级页面，不创建新的 Tauri 窗口。
- 三个功能不使用共同的资讯页和页签切换；用户返回快捷面板首页后再选择其他入口。
- 每个二级页面都提供明确的返回入口，用户可以回到快捷面板首页。
- 公告和技改详情不在快捷面板中展开，点击后使用系统默认浏览器打开官方原文。
- 页面切换不得重复创建 WebView，也不得导致快捷面板内容被截断。

## 范围

### 包含

- 从西山居 `xoyo.com` 官方页面或页面使用的数据源获取公告。
- 对官方公告进行解析、清洗、排序和分类。
- 独立的公告列表和技改列表。
- 公告与技改的本地缓存、手动刷新和离线降级。
- 使用系统默认浏览器打开西山居官方原文。
- 从西山居官方页面或页面使用的数据源获取服务器列表和开关服状态。
- 按服务器单独查询当前状态。
- 选择一个或多个服务器进行开服监听。
- 在程序运行期间按状态自适应轮询被监听服务器。
- 检测到已确认的“关服 → 开服”变化后主动报告。
- 监听服务器配置的本地保存。
- Windows 10/11 与 macOS 的基本窗口、联网、轮询和报告行为。

### 不包含

- 将 JX3API 作为生产数据源或内置、分发 JX3API Token。
- 在应用内渲染官方公告正文或完整网页。
- 修改、总结或由 AI 解读公告正文。
- 对公告和技改进行后台轮询或主动推送。
- 在应用完全退出后继续监听的系统服务、守护进程或计划任务。
- 系统原生通知；开服报告只使用宠物气泡。
- WebSocket 实时推送；官网没有推送能力时使用有限频率的轮询。
- 服务器延迟、排队人数、负载、历史可用率或 SLA 统计。
- 公告搜索、收藏、分享、评论或账号登录。
- 用户自定义数据源。

## 术语与分类关系

### 公告

- 指本期确定纳入范围的西山居《剑网 3》官方公告列表。
- 公告列表是上层集合，允许包含技改公告。
- 列表按发布时间从新到旧排列。

### 技改

- 指从同一官方公告源中识别出的武学调整公告。
- 技改列表是公告列表的筛选子集，不得混入普通维护、活动、版本宣传等公告。
- 首版以标题包含“武学调整”为核心确定性规则，并允许维护一组经需求确认的同义关键词。
- 如果仅凭列表标题不能稳定分类，允许读取官方详情的纯文本用于分类；不得执行详情页脚本，也不得把正文保存到长期缓存。
- 无法确定是否属于技改时，保留在公告列表，不进入技改列表，避免误报。

关系定义：

```text
技改列表 ⊆ 公告列表
```

## 核心用户流程

### 公告与技改

1. 用户单击宠物打开快捷面板。
2. 用户直接点击“公告”或“技改”入口。
3. 快捷面板进入对应的公告或技改二级页面。
4. 应用优先展示有效缓存；需要时从西山居刷新并完成解析、清洗和分类。
5. 用户点击某条记录，系统默认浏览器打开对应的西山居官方原文。

### 单独查询开服状态

1. 用户在快捷面板首页点击“开服状态”，进入对应的二级页面。
2. 用户选择或搜索服务器。
3. 用户点击查询，应用从西山居数据源获取最新状态。
4. 界面显示服务器名称、开服/关服/未知状态和本次查询时间。

### 开服监听

1. 用户选择一个或多个服务器并开启监听。
2. 应用立即查询一次并建立初始状态，不因初始结果主动报告。
3. 程序在运行期间按约定周期轮询被监听服务器。
4. 服务器先被确认处于关服状态，之后被确认处于开服状态。
5. 应用主动报告该服务器已经开服，并更新界面中的状态和时间。
6. 用户可以随时停止单个服务器或全部服务器的监听。

## 需求说明

### 1. 公告与技改列表

- 公告与技改均支持分页加载，不设置只展示最近 `20` 条的总量上限。
- 首版每页展示 `10` 条，并提供上一页、下一页和当前页码。
- 首次只请求第一页；用户翻页时再加载对应页，避免一次获取全部历史记录。
- 每条至少展示：
  - 原始标题；
  - 发布日期或完整发布时间；
  - 可稳定获得时展示官方分类；
  - 技改识别标记。
- 标题最多显示两行，超出部分省略，不得修改原始含义。
- 公告页允许显示技改项；技改页只能显示识别为技改的项。
- 两个页面使用同一份规范化公告数据和同一套分页缓存，不能分别重复抓取官网。
- 技改页需要继续向后筛选官方公告，直到凑满当前页、官方数据已经结束或达到合理的单次请求保护上限；不能因为某一页没有技改就错误显示为全部加载完成。
- 不加载远程封面图、广告图、追踪脚本或其他非必要资源。

### 2. 公告刷新与缓存

- 首次打开且没有缓存时立即请求。
- 存在不超过 `10` 分钟的成功缓存时直接展示，不自动重复请求。
- 缓存超过 `10` 分钟时先展示缓存，再尝试刷新。
- 用户手动刷新时忽略缓存新鲜时间并立即请求。
- 同一时间只允许一个公告刷新请求。
- 请求超时建议为 `10` 秒。
- 成功响应按数据页写入本地缓存；失败响应不得覆盖已有成功缓存。
- 缓存仅保存列表所需字段和分类结果，不保存 Cookie、登录信息、网页脚本或完整正文。

### 3. 公告详情跳转

- 点击记录后使用系统默认浏览器打开原始官方链接。
- 仅允许打开 `https` 链接，并校验目标属于已确认的西山居/金山官方域名。
- 链接不符合允许范围时阻止打开，并显示可恢复错误。
- 首版不在应用 WebView 中加载公告详情。

### 4. 服务器状态模型

内部统一使用以下三态，不让界面直接依赖外部字段值：

```text
Unknown：请求失败、数据缺失或无法识别
Closed：已成功读取并明确判定为关服
Open：已成功读取并明确判定为开服
```

- 网络错误、超时、解析失败和服务器未找到一律为 `Unknown`，不得当作 `Closed`。
- 单独查询每次都发起实时请求，不使用公告的十分钟缓存。
- 可以在短时间内合并同一批服务器的重复请求，但界面必须显示实际数据时间。
- 查询结果至少展示服务器名、状态、查询时间；可稳定获得时展示所属大区。

### 5. 轮询与状态变化

- 只有用户明确开启监听的服务器才参与轮询。
- 使用自适应轮询，不采用固定 `60` 秒高频查询：
  - 状态为 `Closed` 或尚未取得有效基线时，每 `5` 分钟查询一次；
  - 从已确认的 `Closed` 首次查询到 `Open` 时进入待确认状态，`30` 秒后复查；
  - 两次成功样本均为 `Open` 才确认开服并报告；
  - 确认进入 `Open` 后降低为每 `15` 分钟查询一次；
  - 再次确认 `Closed` 后恢复每 `5` 分钟查询。
- 多个服务器应优先通过一次服务器列表请求统一判定，不能为每个服务器分别制造相同请求。
- 首次成功查询只建立基线，不主动报告。
- 仅 `Closed → Open` 触发开服报告。
- `Unknown → Open`、首次查询得到 `Open`、刷新页面或应用启动时直接得到 `Open` 均不触发报告。
- 两次开服样本之间必须间隔至少 `30` 秒，不能用同一响应或立即重复请求完成确认。
- 请求失败只记录为未知样本，不覆盖最后一次已确认状态，也不触发报告。
- 待确认阶段的复查失败时取消本次候选状态，回到正常五分钟轮询，不进行连续快速重试。
- 同一次开服变化只报告一次；状态再次被确认关服后，才允许下一次开服报告。
- 应用从系统睡眠恢复或网络恢复后立即补查一次，仍按上述状态机判定。
- 应用完全退出后不轮询；下次启动先重新建立基线，不补发退出期间可能发生的变化。

建议的状态机：

```text
首次有效值 ──> 建立基线
Closed ──5 分钟轮询发现 Open──> 30 秒待确认
待确认 ──再次确认 Open──> 气泡报告一次并进入 Open
Open ──15 分钟轮询确认 Closed──> 进入 Closed，恢复 5 分钟轮询
任意状态 ──请求失败──> 保留最后确认状态，不报告
```

### 6. 主动报告

- 报告内容至少包含服务器名称和“已开服”。
- 同一状态变化不得连续重复报告。
- 主动报告不能抢占正在进行的拖动、悬停等高优先级宠物交互。
- 报告失败不得影响下一轮状态查询，也不得使宠物主窗口崩溃。
- 开服主动报告只使用宠物气泡，不申请或发送系统原生通知。

### 7. 监听配置

- 用户可以开启或关闭单个服务器监听，并可一键停止全部监听。
- 监听服务器列表持久化保存，应用重启后恢复监听配置。
- 最后确认状态只用于界面参考；重启后必须重新建立监听基线，不根据过期状态补发通知。
- 官方服务器更名、合服或移除时，原监听项标记为不可用，不能静默映射到其他服务器。

### 8. 数据源边界

- 公告、技改和服务器状态的生产数据均直接来自西山居 `xoyo.com` 官方页面或页面实际使用的数据源。
- 开发前必须分别确认：
  - 实际请求地址和 HTTP 方法；
  - 字段、编码、分页和时间格式；
  - 开服与关服原始值的含义；
  - 是否需要页面 Cookie、来源头或动态参数；
  - Windows 与 macOS 网络环境下的可访问性；
  - 合理的请求频率和缓存策略。
- 如果数据需要登录、验证码、签名绕过或其他规避访问控制手段，本期停止接入并回到需求讨论，不实施绕过。
- 网络请求由 Rust 平台层负责，Vue 不直接跨域请求远程站点。
- 远程响应转换为应用内部稳定模型，界面不得直接依赖外部字段结构。
- 外部文本按纯文本处理，不允许注入 HTML。
- 数据适配器必须隔离公告解析、技改分类和服务器状态解析，便于官网改版后单独替换。
- JX3API 仅用于调研和行为参考，不作为运行时回退源，避免两个来源产生状态冲突。

### 9. 状态、错误与安全

- 首次加载显示明确的加载提示。
- 没有缓存且公告请求失败时显示失败原因、重试按钮和“打开官网”入口。
- 有公告缓存且刷新失败时继续显示缓存，并提示当前为上次数据。
- 空列表与请求失败必须是不同界面状态。
- 服务器状态无法获取时显示“未知”，不能误显示“关服”。
- 官网数据格式变化时记录本地开发日志，并向用户显示通用的暂时不可用提示。
- 错误不得影响宠物、快捷面板、设置和托盘功能。
- 不要求用户登录剑网 3、西山居或第三方服务。
- 不接收、存储或执行远程 JavaScript。
- 网络访问和浏览器跳转使用明确域名允许列表。
- 如果请求全部由 Rust 完成，不扩大 WebView 的 `connect-src`。

## 技术方案

- 在现有快捷面板 Vue 视图中增加首页与公告、技改、开服状态三个二级视图的切换，不新增独立 Tauri 窗口。
- 快捷面板首页直接展示三个入口；每次只进入一个二级视图，返回时恢复快捷面板首页。
- Rust 增加：
  - 西山居公告适配器；
  - 技改分类器；
  - 西山居服务器状态适配器；
  - 轮询调度器和开服状态机；
  - 缓存、配置保存与链接允许列表。
- 轮询调度器由应用级状态持有，不依赖快捷面板保持打开；宠物程序运行时仍可监听。
- Vue 只消费内部模型，负责分页列表、查询、监听配置、加载和错误状态。
- 外部数据解析和状态转换写成纯函数，使用固定样例做自动化测试。
- 将缓存、数据源、分类器和通知通道分别抽象，避免官网改版或报告形式变化波及整个功能。
